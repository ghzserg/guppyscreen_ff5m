# Правила для AI-агентов GuppyScreen

## Перед изменениями
- Работать от актуального `main`: получить последние изменения, проверить уже принятые PR и зафиксировать базовый коммит. Перед отправкой повторно сравнить ветку с `main`.
- Делать только запрошенное. Не менять сторонние библиотеки, субмодули, сборочные настройки и несвязанные файлы без необходимости.
- Сохранять API, поведение и поддержку AD5M, AD5X, C5 и C5 Pro. Не увеличивать без нужды расход памяти, число перерисовок, блокировок и копирований.
- В тексте писать **Z-Mod**; не переименовывать ради этого пути, переменные, команды и URL.

## Один diff — одно изменение
- **Сначала собрать один общий unified diff (`.patch`) для всех затронутых файлов.** Проверить его целиком (`git apply --check`) и применить **за один раз** (`git apply`). Не править и не отправлять каждый файл по отдельности.
- Затем проверить `git diff --check`, выполнить тесты и создать **один коммит** с этим изменением. Не разбивать одну задачу на серию пофайловых коммитов.
- Если доступный инструмент не поддерживает применение общего патча, сообщить об ограничении; не подменять этот порядок незаметными пофайловыми изменениями.
- Diff должен быть минимальным: без попутного рефакторинга, форматирования и переименований. Код — простой и лаконичный; не выделять функции ради пары строк.
- Новые комментарии — только необходимые и на русском. Существующие без причины не переписывать.

## Проверка и PR
- Запускать подходящие тесты (`make test`, при необходимости `make test SANITIZE=1`) и затронутые сборки. Не писать «проверено», если запусков не было.
- Для UI прикладывать реальные скриншоты **до/после** в одинаковых условиях. Если недоступны — явно указать это.
- Для каждого PR нужны аппаратные замеры памяти до/после **на одном устройстве** при одинаковом сценарии, после стабилизации: модель, коммиты, `VmRSS`, `VmHWM`, `RssAnon`, `RssFile`, `VmData` и разница в КБ. Если доступа нет — отметить как невыполненные и запросить их; измерения на x86 не заменяют замеры на принтере.
- Не отправлять изменения в GitHub без запроса пользователя и не создавать новый PR, пока предыдущий PR этого агента открыт.
- В конце кратко указать результат, затронутые файлы, проверки и ограничения; приложить общий `git diff` или `.patch`.

## UI-Review
- Для изменённого интерфейса добавить **в описание PR** строку, например: `UI-Review: home, pid, system`. Указывать только нужные экраны, до **8** за запуск. Каждый экран снимается до/после на C5 Pro (purple), AD5X (green) и AD5M (blue) автоматически; тема одинакова для обоих коммитов, модели в строке не указываются. Без строки UI-Review не запускается.
- Список экранов, пути вроде `settings/System` и задержки вроде `home@1200` определены в `ci/ui-review-request.py`. Кнопки, выполняющие действия на принтере, не считать экранами.
- В основном репозитории ревью PR автора `ghzserg` запускается автоматически. Для остальных авторов с веткой в основном репозитории нужна метка **«Готов к ревью»**, поставленная `ghzserg`.
- Для PR из форка проверка выполняется в самом форке через `UI review (fork)`: включить Actions; запуск — при push в ветку с открытым PR и `UI-Review:` или вручную. Результат и ссылку на запуск приложить к PR; в описание основного PR снимки автоматически не публикуются.
- Не добавлять в PR разовые PNG, сценарии, `pr-assets` и новые workflow. Для повторного ревью достаточно нового коммита или обновления `UI-Review:` (в форке — push либо ручной запуск). При необходимости использовать `ci/ui-review.sh` и `ci/publish-review.sh`.
- **Галерея C5 Pro** в `docs/screenshots/c5pro/` — исключение: обновлять её только вручную через GitHub Actions → **Rebuild C5 Pro gallery**, не на каждый PR. Темы экранов чередуются в порядке blue, red, green, purple, pink, yellow по кругу.
