# Правила для AI-агентов GuppyScreen

1. **Название проекта:** в тексте всегда писать **Z-Mod**. Имена файлов, переменных, команд и URL не переименовывать ради этого правила.
2. **Минимальный diff:** исправлять только поставленную задачу. Предпочитать небольшие точечные патчи; не выполнять попутный рефакторинг, массовое форматирование и переименование.
3. **Комментарии:** добавлять только там, где без них неочевидны причина или ограничения решения. Новые комментарии писать на русском; существующие не переписывать без необходимости.
4. **Функции:** не выделять в отдельные функции несколько простых строк, если это не устраняет реальное дублирование и не улучшает понимание кода.
5. **Стиль:** код должен оставаться компактным, читаемым и лаконичным. Не усложнять архитектуру и не добавлять зависимости ради локального исправления.
6. **Pull request:** не создавать новый PR, пока предыдущие PR от этого агента не приняты или не закрыты. Учитывать, что код может измениться и потребовать перебазирования. Не отправлять изменения в GitHub без явного запроса.
7. **Изменения интерфейса:** прикладывать скриншоты **до** и **после** в одинаковых условиях. Если получить их невозможно, прямо сообщить об этом и не выдавать проверку интерфейса за выполненную.
8. **Актуальная база:** каждое изменение должно основываться на актуальном коде репозитория. Перед работой обновлять целевую ветку, учитывать уже принятые PR и фиксировать исходный коммит. Перед отправкой PR повторно сверять изменения с актуальной базой; не использовать устаревшие файлы или патчи вслепую.
9. **Границы изменений:** не затрагивать несвязанные файлы, внешние библиотеки, Git-субмодули и сборочные настройки без необходимости. Любое такое изменение объяснять отдельно.
10. **Совместимость и ресурсы:** сохранять существующее поведение, API и поддержку AD5M/AD5X/C5/C5Pro. Учитывать ограниченные ресурсы устройства; не добавлять лишние выделения памяти, копирования, блокировки и опасные асинхронные обращения к уничтоженным объектам.
11. **Проверка:** выполнять подходящие тесты (`make test`, при необходимости `make test SANITIZE=1`) и проверять затронутые сборки. Не утверждать, что тесты или проверка на устройстве прошли, если они не запускались.
12. **Замеры памяти:** для каждого предлагаемого PR необходимы два реальных замера: **актуальный код до изменений** и **тот же код после применения PR**. Измерять в одинаковых условиях на одном устройстве, после стабилизации работы; указывать коммиты, модель устройства, сценарий и значения `VmRSS`, `VmHWM`, `RssAnon`, `RssFile`, `VmData` из `/proc/<pid>/status`, а также разницу в КБ. Если доступа к устройству нет, запросить замеры у автора PR и явно пометить проверку как невыполненную. Не заменять измерения теоретическими оценками.
13. **Результат:** кратко сообщать, что и зачем изменено, какие файлы затронуты, что проверено и какие ограничения остались. Для исправлений по возможности предоставлять обычный `git diff` или `.patch`.

14. **Подготовка ревью:** для изменений интерфейса запускать `bash ci/ui-review.sh <base-sha> <pr-sha> <scenario.txt> /tmp/guppy-review`. Получить исходные PNG, `review.md`, данные памяти x86. При отсутствии принтера честно писать, что аппаратные измерения не проводились. Даже повтор одного SHA может иметь небольшой разброс VmRSS.
15. **Скриншоты и сценарии:** только реальные framebuffer принтера или тестовый LVGL 800×480, без изменения размеров PNG или цвета. `ci/ui-scenarios/example.txt` — один пример; конкретные сценарии PR создавать временно вне git. Не добавлять в PR PNG, новые сценарии и workflow каждого экрана.
16. **Публикация:** скриншоты должны быть видны прямо в описании PR, а не только в ZIP. После генерации отчёта выполнить `bash ci/publish-review.sh /tmp/guppy-review`: PNG размером до 1 МиБ загружаются на img402.dev без регистрации, сервис возвращает публичный URL без срока истечения, создаётся `review-public.md` с изображениями и таблицей памяти. Вставить текст отчёта в PR через GitHub/`gh`; не использовать локальные пути и ссылки на архив. Загружать только снимки, разрешённые к публичному размещению и не содержащие конфиденциальных данных. Если загрузка недоступна, прямо сообщить об ошибке, не выдумывать URL; для крупных PNG и альтернативы можно использовать вложения GitHub через `gh pr edit --attach` или веб-интерфейс. Ветки `pr-assets` и PNG в git не создавать.
17. **Стоимость:** собирать доказательства после завершения разработки, а не после каждого промежуточного изменения; не пересобирать проект ради правки текста PR. Для одинаковых SHA `ui-review.sh` переиспользует уже собранный тестовый бинарник.
